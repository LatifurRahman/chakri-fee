# Regression and release test plan

## Scope and closure rules

This matrix covers the V1 specification, business invariants, realistic abuse/failure modes and release operations. No finite test suite can cover every possible input, browser, network state or attack. Each family below requires boundary and representative cases. A passing local/CI suite closes automated cases only; a production gate is not closed by a mock or a skipped deployment.

P0 = blocks publishing or corrupts/exposes data. P1 = required V1 behavior. P2 = quality and operational confidence. Test data must live in separate disposable databases. Production smoke tests are read-only; synthetic submissions never enter genuine public statistics.

## Execution order

1. Freeze the matrix and record existing CI status.
2. Add missing tests. Fix a failing behavior only when the V1 specification or safety invariant supports the fix.
3. Run lint, strict TypeScript, unit/API tests and isolated PostgreSQL integration tests.
4. Build optimized production output; run browser regression, responsive and axe checks. Run bounded local performance/smoke probes.
5. Commit/push the verified changes. Observe the new GitHub Actions run and inspect every job; fix failures and repeat only affected checks.
6. Run deployment only after hosting and production secrets are configured. A skipped/unconfigured CD job is a pending release gate, never a completed deployment.
7. Run read-only deployed smoke plus real CAPTCHA, trusted IP, backup/restore and manual accessibility acceptance against staging before public launch.

## Regression selection

Every push/PR runs core CI. Full browser regression runs on main and PRs. Deployments use only main after passing checks. Business/security changes require boundary cases and database/API coverage; UI changes require responsive/error/accessibility checks. Provider quotas and production behavior must be revisited before a traffic campaign.

## Test-data and load-test safety

Embedded PostgreSQL and browser test clusters are temporary. CI uses a separate PostgreSQL service. Tests refuse a nonempty test database. Load tests run against localhost with bounded concurrency and do not send anonymous submissions to production. Production API checks never disclose IDs or security metadata. Hosting/database secrets belong in provider environments or GitHub encrypted secrets, never in chat, fixtures or tracked files.

## Cloudflare migration regression extension

All original case families remain required. Additional cases: CF-DB-01 request-owned PostgreSQL clients with `prepare:true` / `fetch_types:false`; CF-DB-02 parallel request isolation and fresh reads after a moderation write; CF-DB-03 close connections after streamed responses/cancellation; CF-IP-01 accept edge CF-Connecting-IP and ignore spoofed forwarding headers; CF-IP-02 missing/malformed source fails closed; CF-AUTH-01 scrypt verification/signed cookies in workerd; CF-CAP-01 production Worker refuses development bypass; CF-DEP-01 Hyperdrive ID/cache/origin acceptance and disabled release gate; CF-BUILD-01 both build toolchains and typechecks without generated declaration collisions; CF-UI-01 reuse unchanged production browser regressions in workerd; CF-CD-01 only CI-approved main can deploy with explicit enable flag; CF-SMOKE-01 ten read-only HTTPS routes after deploy. Automated local Hyperdrive emulation is not a test of remote pooling/TLS; real staging acceptance remains required.
