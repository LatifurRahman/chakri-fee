# Cloudflare Workers + Hyperdrive + Supabase deployment

Architecture: **GitHub → GitHub Actions CI → Cloudflare Workers → Hyperdrive → existing Supabase PostgreSQL**, with Turnstile. This is a full server application, not a Pages/static export. No D1, schema changes, production seeds, or database reset are introduced by this migration.

## Adapter and compatibility decision

Cloudflare's [current Next.js guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/) recommends **vinext** for Next.js 16. This branch pins vinext / `@vinext/cloudflare` 1.0.1, Vite 8.3.3, Cloudflare Vite plugin 1.62.5 and Wrangler 4.147.0. vinext reimplements Next APIs on Vite; it does not consume `next build`. The separate `npm run build` / `npm run dev` / `npm start` remain standard Next.js. Wrangler configuration is retained as requested; upstream initialization now defaults to the newer `cf` config tool, but its Wrangler path remains supported. Never run init against this configured project just to deploy it.

The compatibility scan reports support for all Next imports/config used here. That static scan is not a production guarantee. vinext is described as beta in the current Cloudflare guide; test upgrades deliberately. Vitest was upgraded from 3 to 5 for Vite 8 compatibility; every original test remains.

[`postgres`](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-drivers-and-libraries/postgres-js/) is supported (minimum 3.4.5; this project uses a newer locked version). Workers use `nodejs_compat`, compatibility date 2026-10-06, `prepare:true`, `fetch_types:false`, at most five sockets per request, and a request-owned client. **Do not use `prepare:false` with Hyperdrive.** It remains valid on the separate Node/Supabase pooler development path. The Worker wrapper retains connections through streaming and closes them through `waitUntil` when response consumption finishes/cancels. It never shares sockets across requests. Cloudflare recommends `pg` first, but retaining supported Postgres.js avoids changing existing SQL/business logic.

[Disable Hyperdrive query caching](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/): cached reads are not invalidated by writes and would change submission/moderation behavior. Pooling still works. The production preflight verifies caching is disabled and the Hyperdrive origin matches the migration database.

## Local development and Workers preview

Requires Node 24, PostgreSQL 17+ and `npm ci` including dev dependencies.

1. Standard Next development is unchanged: copy `.env.example` to `.env.local`, set `DATABASE_URL`, local security secrets and `SITE_URL=http://localhost:3000`, then `npm run dev`. `DEV_BYPASS_TURNSTILE=true` is permitted only by the Node development server, never a production build.
2. For Workers development create ignored `.dev.vars` with the application runtime variables/secrets from the table below, using `SITE_URL=http://localhost:5173` and `TURNSTILE_HOSTNAME=localhost`. Do **not** copy the Cloudflare API token or migration database credentials into `.dev.vars`.
3. Set `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE` in your terminal to a **development** PostgreSQL URL. Wrangler's checked-in fallback is local PostgreSQL on port 5432; its production Hyperdrive ID is deliberately all-zero and cannot pass the release gate. This override is local only, not a remote Hyperdrive tunnel. Never point a local preview at production.
4. `npm run dev:cloudflare` runs vinext in workerd. For the production build use `npm run check:cloudflare`, `npm run build:cloudflare`, then `npm run preview:cloudflare` (default port 4173; change `.dev.vars` origin accordingly). Provide the public site key at build time. A real localhost-enabled Turnstile widget is needed for successful manual submission in production preview. The production preview refuses `DEV_BYPASS_TURNSTILE=true`.
5. `npm run types:cloudflare` generates ignored binding declarations without globally replacing Node/browser runtime types. `npm run test:cloudflare` needs a Workers build and installed Chromium. It creates its own temporary PostgreSQL DB, replaces/restores the ignored generated preview config, exercises the compiled Worker and reuses the unchanged production browser tests. It never touches the configured development/production database.

The wrapper around Vite preserves/restores `next-env.d.ts` and Next's generated route declarations, which vinext otherwise overwrites. Avoid running both build toolchains concurrently in one checkout. `.dev.vars*`, `.env*` except the example, `.wrangler`, `.cloudflare`, `dist`, generated types and test artifacts are ignored. In a restricted execution workspace use writable `XDG_CONFIG_HOME` / `WRANGLER_LOG_PATH` locations; normal developer machines do not need this workaround.

## Exact Supabase steps (manual)

1. Open the **existing production project**. Do not create a replacement or load seeds if it already holds reports. Use a separate staging project for acceptance/load tests. Keep the current region and schema.
2. Take a backup and test restoring to a separate DB before the first deployment. Free-project backup/availability limitations require operator-managed exports and retention; protect backups as sensitive data.
3. In **Connect → Direct connection**, copy the direct PostgreSQL connection details: `db.<project-ref>.supabase.co`, port `5432`, database `postgres`, and the existing server/table-owner role. URL-encode the database password. Include `sslmode=require` for the migration URL. **Do not give Hyperdrive a Supavisor transaction/session pooler URL.** Hyperdrive performs the pooling itself and can reach Supabase's IPv6 direct endpoint; the GitHub migration runner needs connectivity to the direct endpoint too. Check this before enabling production. If your runner cannot reach IPv6, provide an authorized runner with IPv6 or Supabase's IPv4 option; do not silently change origins or disable TLS.
4. Existing migrations are unchanged. If previously provisioned manually, confirm `schema_migrations` accurately records applied migration names before running the migration job; otherwise the original CREATE TABLE statements could conflict. Never mark an unapplied migration as applied. The script holds an advisory lock and uses a transaction; review future migrations before enabling automated deployment.
5. Hyperdrive must connect as the current application server role capable of reading/writing the RLS-protected tables. Current schema has RLS and no anonymous policies; a newly created ordinary role with table grants alone will **not** work. Preserve the current table-owner setup. Never expose an owner connection or Supabase service credential to a browser. A future least-privilege role/RLS redesign needs a separate reviewed migration.
6. Verify **Database settings → SSL configuration** enforces encrypted connections and verify any database network restrictions allow Hyperdrive and the authorized migration runner. Do not use `rejectUnauthorized:false` or publicly expose credentials.
7. Enable `pg_cron` if available and schedule the existing `scripts/cleanup.sql` every ten minutes (Supabase **Integrations/Cron → Create job**, SQL command containing the two DELETE statements). Verify it runs. Without this, expired security hashes can remain stored during inactivity even though active requests clean them.
8. Confirm owner credentials are not in public API policies, review database connection quotas, test rollback/restore and outages in staging. This branch does not change any schema, fee, existing report, or migration file.

## Exact Cloudflare steps (manual)

1. Sign in to the desired Cloudflare account. In **Workers & Pages**, complete the Workers onboarding and choose your `workers.dev` account subdomain. Reserve the origin `https://chakri-fee.<account-subdomain>.workers.dev` (or an existing Cloudflare custom domain). Copy **Account ID** from account details. No Pages project is required.
2. Open **Workers & Pages → Hyperdrive → Create configuration**. Name it `chakri-fee-production`, enter the Supabase **direct** host, port, database, server username and password. Use encrypted PostgreSQL transport and complete its connection check. **Disable query caching** in the configuration settings. If the dashboard does not expose the toggle, run authenticated `npx wrangler hyperdrive update <id> --caching-disabled`. Copy its ID to GitHub `HYPERDRIVE_ID`. Do not commit the password/URL. The deploy script attaches the `HYPERDRIVE` binding automatically.
3. Open **Turnstile → Add widget**. Name it `chakri-fee`, choose Managed, and add the exact production hostname without `https://` or paths. Save the public site key and secret. For staging, use a separate widget/hostname and DB. The application checks Siteverify success, exact hostname and action `fee-report`; the client already sends that action. Tokens are not logged/stored, and local bypass is ignored in production.
4. Open **My Profile → API Tokens → Create Token → Edit Cloudflare Workers**. Scope to this account. Ensure permissions for Workers Scripts edit, Workers assets upload and Hyperdrive **read** (the preflight reads the configuration); add Hyperdrive read to the template if missing. For an optional custom domain, also allow the appropriate zone/Workers route edits. Use token expiry/rotation and least required scope. Save it only as GitHub `CLOUDFLARE_API_TOKEN`; it is **not** a Worker secret.
5. Do **not** connect Cloudflare Workers Builds directly to GitHub for automatic push deployment. If already connected, disconnect/disable that build deployment in **Worker → Settings → Builds**. Disable the old Vercel Git deployment/project integration too. GitHub Actions is the sole deployment gate.
6. Configure GitHub below and run staging acceptance first. When a successful gated release creates the Worker, inspect **Worker → Settings → Bindings** for `HYPERDRIVE` and `ASSETS`, and **Variables and Secrets** for the four version-bound secrets and public settings. Wrangler supplies them; manually adding them in the dashboard is not necessary and later releases overwrite public vars from GitHub.
7. **Worker → Settings → Domains & Routes**: verify HTTPS on the chosen `workers.dev` address; optionally add a custom domain in your Cloudflare zone. Update `SITE_URL`, hostname and widget allowlist together, then rebuild/redeploy. Keep version preview URLs disabled; a shared production DB with per-version hostname changes is unsafe. Local preview is available without remote preview URLs.
8. Inspect **Metrics** and errors. App observability is disabled by default to avoid unsolicited technical-data retention; enable Workers Logs only after configuring sampling/retention and reviewing privacy disclosures. Do not log form values, cookies, tokens, raw source IPs or database/provider response bodies.
9. Leave deployment disabled until the release gates below are met. Hyperdrive/Supabase throughput, CPU and request quotas still apply; national-scale reliability is not guaranteed by free plans.

## GitHub Actions: exact configuration

Create **Repository Settings → Environments → production**. Restrict deployments to `main`; add required reviewers if your GitHub plan supports them. Then set **Settings → Secrets and variables → Actions** (or the production environment for all values except the enable flag). The enable flag must be a repository Actions variable because it is evaluated before the environment job starts.

| Name                             | Location                                                  | Purpose                                                                                                                                              |
| -------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ENABLE_PRODUCTION_DEPLOY`       | **Repository Actions variable: `false`**                  | Explicit opt-in after setup/review. Unset also means disabled. Keep false now.                                                                       |
| `CLOUDFLARE_ACCOUNT_ID`          | Actions/environment variable                              | Destination account ID, 32 hex characters.                                                                                                           |
| `HYPERDRIVE_ID`                  | Actions/environment variable                              | Real cache-disabled production Hyperdrive configuration ID.                                                                                          |
| `SITE_URL`                       | Actions/environment variable → Worker var + build setting | Exact public HTTPS canonical origin; no path/query/fragment.                                                                                         |
| `TURNSTILE_HOSTNAME`             | Actions/environment variable → Worker var                 | Exact hostname of that origin, allowed by Turnstile.                                                                                                 |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | Actions/environment variable → client build + Worker var  | Public key for the matching widget. Rebuild when changed.                                                                                            |
| `NORMAL_FEE_MAX`                 | Optional Actions/environment variable → Worker var        | Default 10000 BDT; larger reports are flagged.                                                                                                       |
| `LEADERBOARD_MIN_REPORTS`        | Optional Actions/environment variable → Worker var        | Default 5.                                                                                                                                           |
| `CLOUDFLARE_API_TOKEN`           | Actions/environment **secret** only                       | Deployment/control-plane authentication. Never a Worker binding/var.                                                                                 |
| `PRODUCTION_DATABASE_URL`        | Actions/environment **secret** only                       | Supabase direct TLS URL for existing migrations; maps to job `DATABASE_URL`. Never a Worker var. Must target the same origin/database as Hyperdrive. |
| `TURNSTILE_SECRET_KEY`           | Actions/environment secret → **Worker secret**            | Server-only CAPTCHA verification.                                                                                                                    |
| `ANTI_ABUSE_SECRET`              | Actions/environment secret → **Worker secret**            | Independent 32+ random character HMAC secret.                                                                                                        |
| `ADMIN_SESSION_SECRET`           | Actions/environment secret → **Worker secret**            | Independent 32+ random character signed-session secret.                                                                                              |
| `ADMIN_PASSWORD_HASH`            | Actions/environment secret → **Worker secret**            | Salted scrypt hash from `npm run admin:hash`, not plaintext password.                                                                                |

Other runtime/build settings and bindings:

- `HYPERDRIVE`: native Hyperdrive binding providing `connectionString`; configured automatically at release from ID. Origin password lives in Hyperdrive, not app code.
- `ASSETS`: native static-assets binding created from `dist/client`. No manual storage bucket, D1, R2 or KV required.
- `nodejs_compat` + compatibility date 2026-10-06 enable Node crypto/AsyncLocalStorage/Postgres socket support and runtime `process.env` population. `NODE_ENV` is compiled to production for production builds; do not configure a runtime override.
- `DEV_BYPASS_TURNSTILE=false` is forced by release script. Do not put a true bypass on a deployed Worker.
- `DEPLOYMENT_TARGET=cloudflare`: job/operator-only validation selector; not required in the Worker.
- `DEPLOYMENT_URL`: job/operator-only read-only smoke target; CI sets it to `SITE_URL`.
- `DATABASE_URL`: standard Node local/migration setting. Production Workers use only Hyperdrive.
- `TEST_DATABASE_URL`: disposable CI PostgreSQL service, never production. The Workers/browser harnesses create separate temporary databases.
- `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE`: local emulator override only; never deploy it.

Generate the two independent random secrets with `openssl rand -hex 32`; generate the admin hash interactively with `npm run admin:hash`. Enter them through protected dashboard/secret inputs, never issue bodies, committed config or chat. Worker release secrets are written to a temporary file with mode 0600, uploaded atomically with the version via `wrangler deploy --secrets-file`, then deleted. Public build settings are recorded in the ignored artifact and checked against the release to prevent mismatched widget keys/origins.

CI runs on main, PRs, manual dispatch and the migration branch. No production job runs on the migration branch or PR. Check job requires clean install, zero-warning lint, production audit, all unit/Postgres tests, original Next build/typecheck, Chromium/Firefox browsers, Next production browsers, compatibility scan, Workers build and actual workerd/database/browser regression. The deployment job has `needs: check`, requires `main` and `ENABLE_PRODUCTION_DEPLOY=true`, and respects the production environment. It validates configuration, rebuilds with production public settings, checks remote Hyperdrive/cache/origin, applies the **unchanged** transactional migration runner, deploys through pinned Wrangler and runs the existing ten-route **read-only HTTPS smoke**. It never inserts fake reports.

Changing this branch does not merge it or enable deployment. Once production configuration and staging acceptance are ready, explicitly review/merge the branch, set the repository enable flag to true, and dispatch the workflow on main (or let the next main push run its gated flow). To deploy manually as an authorized operator, load the same variables securely, set the enable flag explicitly, build, run preflight/migrations, then `npm run deploy:cloudflare` and `DEPLOYMENT_URL=<SITE_URL> npm run test:smoke`. Do not bypass GitHub CI for routine production releases.

## Release acceptance, rollback and risks

Local tests verify compiled workerd with a real disposable PostgreSQL origin, not remote Hyperdrive pooling/TLS, actual Supabase networking or a live Turnstile challenge. Before enabling production, verify staging: real CAPTCHA success/replay/expiry and exact hostname/action; edge-overwritten `CF-Connecting-IP` even with forged `x-real-ip`/forwarded headers; shared rate limits; valid anonymous submit → fresh stats; admin approve/reject/rename/merge; no unapproved data in public views; mobile/Safari/screen readers; DB outages; cleanup; and backups/restore. Inspect origin usage and Worker CPU/size at realistic concurrency.

**Source header:** the Workers request context reads only `CF-Connecting-IP` supplied by Cloudflare. It ignores spoofed `x-real-ip` and `x-forwarded-for`. Disable Cloudflare's “Remove visitor IP headers” transform for this Worker path, and avoid cross-zone Worker proxy chains that alter source identity; verify the actual edge route in staging. Node production retains its existing trusted `x-real-ip` contract. Missing/malformed addresses fail closed. IPs are processed transiently and stored only as short-lived daily HMACs, never in public reports.

`scryptSync` is supported and exercised in workerd but is intentionally CPU intensive: the free Workers CPU allowance may be insufficient for admin login or full SSR/database work. Size and CPU limits are separate from passing local emulation. Confirm whether Workers Paid is necessary before launch; do not weaken password hashing to meet a free quota. Supabase Free can pause and has storage/backup quotas, and Hyperdrive has query/connection limits. No free configuration promises availability for a large population.

For rollback, leave the prior Worker deployment/version available and use **Worker → Deployments → previous deployment → Roll back** (or authenticated `wrangler rollback <version-id>`). Review version-bound secrets, widget/domain compatibility and database compatibility. Rollback does not reverse migrations; this branch changes none. If post-deploy smoke fails the workflow is red even though the new deployment may already be live: investigate and perform a reviewed rollback, do not assume a failed job automatically restored it. Keep a secure database backup and a tested recovery procedure.

### Additional dependency audit finding

The requested `npm audit --omit=dev --audit-level=high` passes. A separate **full toolchain** audit also found upstream advisories in `braces` (deeply nested glob patterns, high) and `fflate` (malformed ZIP64, moderate), with no fixed versions offered by npm at verification time. They are pulled through lint/glob tooling and vinext's unused image-generation dependency. The checked-in Open Graph PNG does not accept font/ZIP uploads, and no user form value is used as a build glob. Neither package name nor `unzipSync` appeared in the inspected compiled Worker JS. This does not make the upstream advisories disappear: treat build inputs as trusted, monitor those advisories, and deliberately update/retest when upstream fixes arrive. The full audit is not green; do not describe all development dependencies as vulnerability-free.
